# 21. The Companion Channel is a surface the user replies on: an Anchor names the target, a numeral picks the option

Date: 2026-09-06 · Status: Accepted · Source: map [#246](https://github.com/okqixiaobao727-design/GPT-VoiceCoding/issues/246), requirements page Notion `0905_telegram` (Simon, 2026-09-05), decided on [#247](https://github.com/okqixiaobao727-design/GPT-VoiceCoding/issues/247)–[#259](https://github.com/okqixiaobao727-design/GPT-VoiceCoding/issues/259)

The Companion Channel today is a notification outlet with a typed command line behind it: every Stop reaches Telegram as `briefing.text`'s labelled lines, and a reply has to be `@<name>: words`, `/command` or `>prompt`, or bare text that the router (`core/router.py`) accepts only when exactly one Session is live. Away from the Mac that is not a surface a person lives in — the notice reads like a log line and answering it means typing a Session Name on a phone. The requirements page asks for four things: receive what a Session stopped on with the agent's own words, reply by replying to a message, no log feel, no tmux. Two options were on the table: keep Telegram a peer of the Live Call on Bridge Core, or route everything through a model (a Delegate) that reads the chat and decides. This ADR takes the first and records the whole shape the map settled, because the shape is one mechanism repeated — a message the user can reply to, carrying choices a numeral picks — and the implementation issues are cut from it.

**Standing rule for everything below** (Simon, 2026-09-05): this is an *extension* of the current architecture, never a redesign of it. Every Telegram behaviour reduces to filling the target and the words of today's `relay <target> <words>` and `approve <id> <verdict>`; seams grow optional fields at most; no layer changes shape. And one rule set across surfaces: Voice, Control Panel and Telegram all end in the same two verbs, and only *who fills the target and the label* differs — the Call Agent on the call, a button on the panel, a reply anchor plus a numeral on Telegram.

## Decision

### 1. Telegram stays a peer surface on Bridge Core; a model never classifies inbound text

Inbound words reach the Session directly, on the routes ADR 0013 and ADR 0015 already own; a Delegated Turn is involved only when the user asks for one. Routing is deterministic and Bridge Core's (ADR 0001: classifying inbound Companion Channel text is the hub's job). A model renders prose and answers questions; it never decides which Session a message was for. The requirements page's second option — every message through a Delegate — is refused because it moves the user's authority out of their own hands: an Answer Relay carries the user's words as theirs, and a model between the user and the Session would be a second author of them.

### 2. The target of a reply is the message it replies to: the Anchor

Every outbound message that names one target is an **Anchor** (`CONTEXT.md`). Bridge Core keeps the **Anchor Table**: the map from the provider's message id — every part of a split send, against one row — to what a reply to it means. A row holds the anchor's kind, its target (a `SessionTarget`, or an Assistant Conversation's thread id — §7), its option labels in order (may be empty), the pending approval id when it carried a permission, and when it was sent. It holds neither the message text nor the Session Name; the name is re-read from the roster.

- **Memory only.** The table is empty after an engine restart, and `state.json` is untouched. Sessions are recognised afresh at every start (ADR 0020); a persisted row pointing at something the engine has not yet re-recognised would be half-reliable, and one plain rule beats that.
- **Rows go with their Session**, and each Session keeps only its newest N rows (configured, default 100). There is no time-based expiry and no timer: a day-old notice is a legitimate thing to reply to.
- **A reply to an unknown anchor** — pre-restart, fallen out, the user's own message — is treated exactly as a message that replied to nothing **when it is words**. A numeral (or a press, which is a numeral) on an unknown anchor is refused with one fixed hint and is never re-targeted: Core no longer knows what that row's options were, and re-reading "2" against the newest anchor would pick a different message's second option (review finding, 2026-09-06). The text Telegram echoes back in `reply_to_message.text` is deliberately ignored: it can be truncated, two notices can share it, and inferring a target from prose is the classification §1 rules out. The message id is the only key.
- **A message that replies to nothing goes to the target of the newest Anchor** — literally "reply to the previous message". On this surface, where messages lie flat, that rule takes the place the Focus Session has on the voice side, which is unchanged. With an empty table today's rule stands: exactly one live Session receives it, otherwise the existing refusal that names the candidates. This fall-through is for **words only**: a numeral that replies to nothing — typed in the chat bar under a notice rather than as a reply to it — is refused with the same fixed hint as a numeral on an unknown Anchor, whatever the table holds, because a numeral is a decision over one specific question and a notice can land between the user reading the screen and typing (ruled on #263, 2026-09-06).
- **`@<name>: words` survives as a fallback**, not the main path. The command menu and every button exist only to produce Anchors.

### 3. The reply grammar: a numeral picks, anything else is the user's words

- **A numeral picks that Anchor's Nth option label.** Before relaying, Core asks the Agent seam whether that Session's decision is *still answerable from here* — the fact ADR 0015 already exposes. If it is, the label goes as an Answer Relay, which the Claude adapter carries through the held `AskUserQuestion` hook (ADR 0015 — the route that carries the user's authority; **not** the Approval Relay, whose verdicts stay `allow` / `deny` / `ask`). If it is not, nothing is sent and the reply says the question was already answered on screen and asks for words. A numeral on a permission notice resolves to a verdict on the row's approval id — §6 — and a numeral on any other anchor kind is refused the same way. Free text is never subject to this check.
- **Any other text is the user's own words, relayed verbatim** through the ordinary Answer Relay — including a `/x` line naming a skill, and including text inside an Assistant Conversation.
- **`>` is a top-level form only**: a one-shot Delegated Turn with no Session context, unchanged. A `>` inside a reply to a Stop Notice is *not* a question about that Session — a reply to a notice is always the user's words to that Session. The Session-level assistant this would have been is refused; §7 is what replaces it.
- **`/` at top level is the control plane; `/` inside a reply belongs to the Session.** The relay wrapper names the act (`run the skill /x with arguments …`), because neither transport expands a leading `/`: measured on [#248](https://github.com/okqixiaobao727-design/GPT-VoiceCoding/issues/248) (Claude Code 2.1.261, `codex-cli` 0.153.0), the Codex rollout stored `/review` literally and Claude's inbox delivered our text verbatim inside Claude Code's own peer preamble, which already tells the receiver to act on it. Whether the skill starts is the Session's own judgement on both lanes, and Bridge Core reports what it did rather than promising it ran. Skills marked `disable-model-invocation` are unreachable by any relay route (measured: `Skill … cannot be used with Skill tool due to disable-model-invocation`); the Session says so and the user types it at the terminal. There is no keystroke injection.
- **No pre-check of a skill name** ([#256](https://github.com/okqixiaobao727-design/GPT-VoiceCoding/issues/256)). The Session resolves the name itself (measured: Claude lists `~/.claude/skills` before calling the Skill tool, Codex reads the skill's `SKILL.md`), so a wrong name costs one turn and is never wrongly refused. A pre-check would be instant and wrong whenever its list was stale or blind to the invocation ceiling, and Bridge Core reads no skill roster from either lane — building one would make the hub know a per-lane fact it has never needed.

### 4. The seam grows optional fields, and a button never crosses it

`seams/companion_channel.py` changes by three optional fields on the way in and out, and one more for §8; nothing changes shape. The null channel stays a real implementation: its `send` returns a `ChannelReceipt` with no ids and its positive non-delivery as today, and it never emits.

- **`InboundText.in_reply_to: str = ""`** — the adapter's opaque id of the message the user replied to, empty when they replied to nothing. It is of the same nature as `origin`: a fact the adapter can see, not an opinion about meaning, so the seam's "no field an adapter could use to volunteer a classification" contract holds. Core matches it by string equality against the Anchor Table and never parses it. A second event type was rejected: it would duplicate `text` and `origin` and add a Core branch doing the same work.
- **`send` returns `ChannelReceipt`**, a `DeliveryReceipt` subclass with `message_ids: tuple[str, ...] = ()` — the provider ids of every part that landed, in order. Chosen over growing the shared `DeliveryReceipt` (three seams use it; Telegram ids do not belong in the Agent or Call vocabulary) and over a tuple returned beside the receipt. An `UNKNOWN` receipt from a split send that failed after a part landed still carries the landed ids, and those parts are Anchors. Core's existing `send` sites keep reading `is_delivered`.
- **`send` takes `origin: str = ""`** — Core echoes the inbound event's `origin` when it replies to that event and leaves it empty for unbidden pushes. This is what the `origin` docstring already promised; Core starts honouring it.
- **A button press is a numeral reply, folded inside the Telegram adapter.** The adapter subscribes to `callback_query` (added to `ALLOWED_UPDATES`; a set list persists on the bot — [#247](https://github.com/okqixiaobao727-design/GPT-VoiceCoding/issues/247), which found that our own `["message"]` list is what had been excluding it). A press becomes `InboundText(text=<position>, origin=<adapter-private value carrying the callback id>, in_reply_to=<pressed message's id>)` — identical to typing that numeral in a reply. Core's reply to that `origin` is shown as a **toast** through `answerCallbackQuery`, never as a chat message: a toast holds ≤ 200 characters and a callback can be answered once, so a longer reply or a second one falls back to a chat message. A toast is no chat message and so registers no Anchor. If `answerCallbackQuery` itself fails, the failure is logged and the reply is sent as a chat message instead. Core never learns the word "button".
- **Text only, this iteration.** A message from the configured chat that carries no `text` (voice note, photo, file — captions are not mined) is raised as `InboundText(text="")` and the router's existing cannot-classify path answers with one fixed hint, worded once in Core. Strangers are dropped silently before this, as today.

`in_reply_to`, `message_ids` and `origin` are opaque strings; a channel with no reply concept emits empty and gets the newest-Anchor rule. `callback_query` and `answerCallbackQuery`, the only genuinely Telegram things, never leave the adapter.

### 5. One vocabulary, three layouts: Core fills a structured brief, the adapter lays it out

The Voice already has the precedent: `briefing.spoken()` fills the Call seam's `SpokenBrief` from Core's wording tables and the realtime adapter assembles it, choosing no words. The Companion Channel does the same. Core fills a **seam-owned structured brief** — state word, agent, name or address, question, option labels, recommendation, the newest message whole, the answerable-here and undelivered wording, and the roster rows for a roster — and the Telegram adapter lays it out. `briefing.text` stays the renderer for `bridgectl brief` and the log, unchanged. The rule in `docs/control-plane.md` — "one renderer is the point: two would be two descriptions of one Session" — is **restated, not broken**: what must not fork is the *words* (the state words, the option labels, the original), and they still come from `briefing.py` alone; layout per surface is what `spoken()` already does. Whether the structured brief crosses as an optional argument to `send` or as a sibling of `SpokenBrief` in a shared `seams/` module is the implementation issue's choice; either keeps the null channel real.

- **The notice shape.** Line one: a state light and the state word (`🟡 waiting for your decision`). Line two: `<agent> · <project> · <task>`. A blank line; the question in bold; the numbered options; a blank line; the original folded. No other symbols. A notice with no question (a turn that ended: `finished`) is the same layout with the question slot empty and the whole answer in the fold — that is the requirements page's "more original content than the delegate's summary", and it needs no special layout.
- **The agent's words are never escaped**, by construction: the adapter sends plain text plus an `entities` array (bold for the question, `expandable_blockquote` for the original — Bot API 7.4 allows it to be given explicitly, offsets in UTF-16 code units which the adapter already counts) instead of MarkdownV2, whose eighteen-character escape list applies inside blockquote bodies too and whose every escaping bug shows up as a refused `sendMessage`. A stray `*`, `_` or backtick in a Claude message cannot break a notice. Code inside the original shows as plain text inside the fold — Telegram forbids `pre` and `code` inside a blockquote — with fences as literal characters. Accepted.
- **A notice is one message.** When headline plus original exceed the adapter's limit, the original is cut to what remains, preferring the last line break then the last space, and the fold ends with a fixed marker (Core's words). The headline is never cut. A `/full` command and a "show more" button that pages History were both refused as too much machinery: the full text is on the terminal. The cut lives in the adapter because the limit is Telegram's; the marker's words are Core's because the vocabulary is the user's. `split_message` stays for the messages that are not notices. **This is the one place a message text is cut.** ADR 0016's rule — text is carried whole or named as omitted, never sliced — still governs what Core reads and carries; the structured brief still holds the original whole. The cut is a layout act on one surface with a hard limit, marked where it happens, and this ADR amends ADR 0016 to that extent and no further (Simon, 2026-09-05, on #251).
- **The roster** is laid out in the same visual language — one line per Session, `<state light> <name> · <agent> · <state word>`, a counts line under it — from the same structured brief, and it is an Anchor (§6).

### 6. Options are labels; a surface that can draw buttons draws one per label

`send` grows no `options` argument: the labels already ride in the structured brief, and the Telegram adapter draws one inline button per label, in order, with `callback_data` the 1-based position (adapter-private, within 64 bytes). One mechanism serves every screen:

- **Question notices**: one button per option label, the label verbatim on the notice line and truncated for width on the button. A press is the numeral of §3.
- **Permission notices — buttons too** (Simon, [#255](https://github.com/okqixiaobao727-design/GPT-VoiceCoding/issues/255)): `allow` / `deny`, from Core's wording table, with the matching numbered lines `1. allow  2. deny` in the notice so a typed numeral works identically. Numeral 1 resolves to `allow` and 2 to `deny` on the pending approval id the row holds — an Approval Relay, the user's own verdict. `ask` gets no button: not answering hands the dialog back to the terminal, which is already the default. **This goes one step past the Control Panel**, which keeps permissions outside its question panel (ADR 0014's panel, still in place); the reason is that approving from away is this channel's core scenario. A Codex Session, which has no hook route, still gets the buttons, and a press gets the honest refusal `approve` gives today.
- **The command menu** ([#253](https://github.com/okqixiaobao727-design/GPT-VoiceCoding/issues/253)) has four entries: `/assistant` (§7), `/sessions`, `/status`, `/config`. **The three new verbs join the shared control-plane command set** (`seams/control_plane.py`, one parser for `bridgectl` and every `/` — `docs/control-plane.md`): `sessions` answers with the roster brief carrying labels, `config` with the config screen, `assistant` opens an Assistant Conversation. `bridgectl` therefore gains the same three, answering in text and ignoring the labels like any surface that draws no buttons. A Telegram-private parser was refused as a second command interface; `setMyCommands` only advertises what the shared set already accepts. Every menu screen is an Anchor carrying option labels: `/sessions` → the roster, one label per live Session — the Roster Brief lists live Sessions only (`CONTEXT.md`), an ended one is announced by §9's line and appears nowhere here — resolving by position and never by label text; pressing a Session → a greeting Anchor for that Session with `brief` / `history` / `send message`; `send message` → the prompt "Say to <name>:" (Core's words) with Telegram's ForceReply, an Anchor with no expiry of its own that a later Stop Notice supersedes by the newest-Anchor rule; `/config` → `switch` / `verify` / `live`; `switch` → one label per switch showing its current state, a press meaning "flip". `/status` is plain text and not an Anchor; `verify` and `live` run at once and answer with text. `relay` and `approve` are folded away on this surface — a reply *is* the relay and a numeral *is* the approval — and `switch`, `verify`, `live`, `brief`, `history` stay typeable. The withheld-from-the-Call-Agent precedent (`status`, `switch`, `verify`) does not apply here: the presser is the user, not a model.
- **Receipts, replies, `/status` and `>` answers** carry no labels and get no buttons.
- **A channel that cannot draw buttons ignores the labels**: the numbered lines are already in the text, so nothing is lost and nothing is appended.

### 7. The assistant is a menu-opened conversation whose memory is the coding model's own thread

`/assistant` opens an **Assistant Conversation** (`CONTEXT.md`): Bridge Core starts a fresh Codex thread with the delegated instructions and the `[delegate] model`, sends a fixed opening line, and that message is an Anchor of a new kind whose row carries the thread id instead of a `SessionTarget`. A reply to *any* message of that conversation resumes the same thread (`thread/resume`, which the Codex Session adapter already uses); every answer is an Anchor of the same conversation. Two conversations coexist, and which one a message continues is decided only by what it replies to. Plain typing goes to the target of the newest Anchor, whichever kind it is — an assistant answer, or a Stop Notice — so §2's rule reads "the target of the newest Anchor", not "the Session of". Every assistant answer carries ForceReply as a courtesy — on its last part when it is split — so the client shows the reply bar and a placeholder; the routing is the Anchor rule and nothing else.

- **No transcript in Bridge Core.** Codex keeps the thread and its rollout; Core keeps the thread id on the row. Assistant Anchors are not a Session's, so they are capped per chat at the newest N conversations (configured, the same policy shape as the per-Session cap). A reply to an expired assistant Anchor, or to a thread that cannot be resumed, gets one fixed hint to start again from the menu.
- **The rest is today's Delegated Turn unchanged**: delegated instructions plus the user's words, no pre-loaded Session facts (the turn reads `brief` / `history` itself, as the Call Agent does); the full delegated action set, `relay` and `approve` included, the turn reporting only what the engine confirmed; the answer as a threaded reply through `send(origin=…)`, a failure sending the error's own words the same way; the "typing" chat action while a turn runs, adapter-owned; one `[delegate] model` setting for every surface. A second reply while a turn is running meets Codex's own refusal of a `turn/start` on a busy thread, and those words come back as the answer — no queueing.
- **A Delegated Turn's thread may now outlive the turn.** The realtime adapter states the opposite ("Fresh thread, one turn, then gone … nothing in the locked decisions asks for continuity between delegated turns"); this decision asks for it. The top-level `>` keeps its one-turn thread; an assistant thread lives as long as its conversation, and each turn still unsubscribes when it ends. The adapter already leaves a thread in place on retire — it interrupts and unsubscribes, never deletes — so the change is the stated rule, not the mechanism.

### 8. A notice whose decision has closed is edited in place, minimally, and stays the same Anchor

When an Anchor's question or permission **stops being answerable from here** — answered from Telegram, answered at the terminal, permission handed back (`ask`, or the hook ending without a verdict), Session ended, Session left the roster — the notice is edited where it was sent: the state line becomes one fixed closed word (`handled`, from the wording table) and the buttons go; the question, the numbered lines and the fold stay as sent, so the chat still reads as a record. Nothing is added — no mark on the chosen option, no "answered from …" line; the user's own reply and its receipt already sit below. The word is fixed rather than the Session's current state, because a notice is the record of one stop, not a live roster row, and tracking later states would mean re-editing on every transition. Core already sees every cause (`ReplyWindowChanged` → CLOSED, an approval settling, `SessionEnded`) and does not distinguish them, because the edit does not show them.

- **Seam: `send` grows `revises: tuple[str, ...] = ()`** — the provider ids from the earlier `ChannelReceipt`. Non-empty means "replace those messages' content with this brief"; the Telegram adapter calls `editMessageText` (same `entities`, inline markup only, no age limit for bot-sent messages), and the null channel ignores it. Core re-fills the same structured brief with the closed word and **empty option labels** — empty labels are what draws no buttons, so no "remove buttons" instruction exists anywhere. A new seam verb was refused as a shape change. The row is untouched: a reply in words still reaches its Session, a numeral is refused as in §3, and `sent_at` is not refreshed, so an old notice never becomes the newest Anchor again.
- **Gating.** A notice edit is not a push: it notifies nobody and only corrects a message already sent. It obeys the Duty Switch like every unbidden act toward the user and **not the Message Switch**, so a notice that is out still closes on screen after the user flips Message off — stale buttons would otherwise invite a press that earns only a refusal. The switches-screen edit below is different in kind: it is the *answer* to a control-plane action the user just took, and ADR 0002 puts it past every switch — Duty included, or the user who flips Duty off from the phone would never see the flip land.
- **Failure is logged and dropped**: an edit Telegram rejects (message deleted, error) or a row that is gone (restart — the table is memory) gets no retry and no fresh message. "Message is not modified" is success.
- **Menu screens: the switches screen only.** After a flip through it, Core re-sends the switches brief through `revises` onto the same Anchor so each label shows the new state. The roster and greeting screens are not edited when a Session ends; a press there gets §6's refusal. A flip made elsewhere edits nothing: the label goes stale and a later press still means "flip".

### 9. What is pushed: every Stop, one line when a Session ends, nothing mid-turn

- **Every Stop pushes one notice**, whatever it stopped on — the code already does this (`core/bridge.py::_session_stopped`), `finished` included, and it stays. No per-state difference, no Focus Session bias, one format with only the state word and the presence of buttons differing.
- **Mid-turn progress is never pushed.** Nothing mid-turn reaches Core today (ADR 0016: status carries no chat body), the requirements page rules out "log feel", a turn in progress has no decision point to reply to, and pushing it would bury the notices that do. It is read on demand through `/sessions` → `history`.
- **A Session's end is announced: one line, new** — `⚫ ended · <agent> · <project>`, no question, no fold, no buttons, on `SessionEnded` from any cause (Core does not distinguish exit, crash or closed terminal). Away from the Mac, "it is gone" is the one fact the user most needs, or they reply to a stale notice and get only a refusal. It is **not an Anchor**: it names a Session that is gone and its rows drop on the same event, so a reply to it takes the unknown-Anchor path. The order on `SessionEnded` is fixed by the ids: edit the Session's open notices to `handled` (§8), push the ended line, then drop its rows. `ended` is a wording entry beside the state words, not a sixth `BriefState` — a brief describes a Session on the roster and this one has left it. Engine shutdown sends no ended lines (Sessions are re-recognised at the next start), and spawned children, which get no Stop Notice, get no ended line.
- **No new Feature Switch.** Every push rides the Message Switch alone. A "questions only" switch, if `finished` notices ever prove noisy, is an independent later ticket.

### 10. Proof: two layers, three real facts, three named steps, states read by product-issued id

Decided on [#259](https://github.com/okqixiaobao727-design/GPT-VoiceCoding/issues/259) against 131 acceptance runs on the machine of record: of 113 `live call` walks, 73 were red; every other step was red under a tenth of the time and `stop notice` never. The "often red, product fine" experience is that one step — a model in the loop, edges graded inside derived windows — and the text side, where this surface lives, is almost never red.

- **The unit layer proves everything deterministic**, in CI in seconds: the adapter's mappings (`callback_query` → numeral reply, `reply_to_message` → `in_reply_to`, `revises` → `editMessageText`, labels → inline keyboard, toast ≤ 200 else message) against `FakeTelegram` **grown** to speak `callback_query` updates, `answerCallbackQuery`, `editMessageText`, `reply_to_message` on inbound and an incrementing `message_id` on `sendMessage`, journaling each edit with the id it was given; and Core's Anchor Table, numeral resolution, newest-Anchor rule, `handled` trigger and ended line against the existing seam fakes.
- **The real-environment run proves three facts only**: words replied to a notice reach *that* Session and it acts; a button press yields a toast and a delivered `relay`; the answered notice is edited to `handled` with its keyboard gone. Three new steps carry them, named now because step names are a contract build tickets cite: **`reply`** (words to a notice, proved by a file effect; the numeral refusal after a terminal answer is a wording and a non-event, so it is unit-proved and never walked), **`button`** (press, toast, edit — on a permission notice as well as a question notice), **`menu`** (`/sessions` → a Session → `send message` → words delivered). `companion inbound` keeps its name and becomes a reply-anchored message; the `@<name>:` fallback is proved at the unit layer only.
- **Never on the `live call` walk.** Every Telegram step runs with Voice off and Message on, on the text-side journey. Taking `live call` out of the pre-merge gate altogether amends the acceptance contract ([#180](https://github.com/okqixiaobao727-design/GPT-VoiceCoding/issues/180)), not this spec, and is [#260](https://github.com/okqixiaobao727-design/GPT-VoiceCoding/issues/260).
- **The grading rule**, for the implementation issues to cite: *each Telegram acceptance observation reads one state keyed by a product-issued id; no observation that needs a waiting window or a wording match may be graded.* The harness takes the receipt synchronously — a Stop Notice is unbidden, so its `ChannelReceipt.message_ids` reach the harness through **one named engine-log record per send**, written under the engine's `getLogger` convention and part of the acceptance contract as the inbound line already is (#48); a relay's ids come back on the `bridgectl relay` reply — then reads the Telegram message once by that id through the user account — a snapshot, not "within N seconds". No negative observations are added; no model output is graded — "the Session acted" is a file effect in the workspace, as today's `relay` step proves it. A read that finds nothing is FAIL, and only two things produce it: the product did not send, or Telegram was unreachable, which preflight already gates. An INCONCLUSIVE grade was refused as naming the uncertainty instead of removing it. Telethon 1.44.0, the run's user-account client, already presses inline buttons, reads keyboards and reply anchors, and re-reads one message by id.
- **The protocol-level e2e fake suite (`docs/e2e-suite-design.md`) is not built.** It would be a third harness, the cost the decision exists to avoid; `FakeTelegram` is already a real HTTP server in the Bot API's shape, and five more methods buy the same determinism.

## Considered and rejected

- *Everything through a Delegate* (requirements page option 2) — breaks ADR 0001 and strips the user's authority from an Answer Relay (§1).
- *A Session-level assistant, `>` inside a reply* — a reply to a notice is always the user's words to that Session; the assistant is reached from the menu instead (§7).
- *Persisting the Anchor Table* — half-reliable across a restart that re-recognises every Session; a plain empty table wins (§2).
- *Inferring the target from the echoed quote* — classification of inbound prose, which this surface never does (§2).
- *A pre-check of skill names* — wrong whenever stale, and Core has no source for it (§3).
- *MarkdownV2* — every escaping bug is a refused send; entities cannot be broken by the agent's words (§5).
- *Fetching a truncated original* (`/full`, "show more") — too much machinery for a text that is on the terminal (§5).
- *A `revise` seam verb, an `options` argument on `send`* — shape changes where an optional field suffices (§6, §8).
- *Editing a notice to track the Session's later states, marking the chosen option, editing rosters on every change* — drift, and a record that stops being one (§8).
- *Pushing mid-turn progress* — log feel; the switches and the Cool-down exist to stop that chatter (§9).
- *The e2e fake suite, an INCONCLUSIVE grade, a window-based observation* — a third harness, and the harness reds this decision exists to end (§10).

## Consequences

**Words.** The state words, the closed word, the ended word, 允许 / 拒绝, the "对 X 说：" prompt, the greeting and config labels, the truncation marker, the non-text hint, the assistant's opening line and the start-again hint are all entries in Core's wording tables (`core/briefing.py` and beside it), chosen by Core and laid out by the adapter, which chooses none. **All of them are English** (Simon, 2026-09-06): the table stays the one it is, the Voice keeps re-rendering it in speech, and the Telegram layout prints it as it stands. The Chinese in the map's mock-ups (`等你做决定`, `已处理`, `已结束`, `允许 / 拒绝`, `对 X 说：`) was the sample layout verified live on 2026-09-05, and the layout survives; the words in it do not. A per-surface language, and an adapter-held translation table, were both refused — the first is a layer of configuration nobody asked for, the second is a second vocabulary, which is the fork §5 exists to prevent.

**Receipts.** A reply's receipt on this surface is **a sentence from Core's wording tables, not the three codes** (Simon, 2026-09-06). `bridgectl relay` keeps printing `state=<state> grade=<grade|none> reason=<code>` — the machine-readable line `docs/control-plane.md` fixes — and the Companion Channel's inbound path answers with it today; under this ADR the path renders those same three facts into one sentence, held once in Core beside the receipt line (`core/relays.py`), and the Telegram adapter prints or toasts it unchanged. That sentence carries the clause ADR 0013's amendment gives the Voice, on the same test: when the words answered a question the Session merely *said* — plain text, no held hook — the receipt adds that the Session may not treat it as the user's own confirmation; an answer through the held-hook route (ADR 0015) and a permission verdict get no such clause, because both carry the user's authority. One rule, one place, two surfaces reading it. Showing the raw codes was refused as the log feel the requirements page rejects, and a sentence without the clause was refused because it would tell the phone user their answer was their own on a route that carries nobody's.

**Docs that describe running code follow the code, not this ADR**: the "one renderer" paragraph of `docs/control-plane.md` and the `companion inbound` row of `docs/acceptance-design.md` are true of today's build and are amended by the implementation issue that changes each, citing §5 and §10 here. The realtime adapter's "does not outlive it" paragraph is amended by the issue that builds §7.

**Earlier decisions, read against this one.** ADR 0001 stands, and this is the ruling with a use case behind it that its "seam verbs extend only through a ruling" clause asks for. ADR 0002 stands: the menu's commands and every typed `/` pass ungated, the switches-screen edit that answers one passes with them, and a notice edit, being no push, is gated by Duty alone. ADR 0013 decision 3 and ADR 0015 stand and are the routes §3 rides: a numeral is an Answer Relay through the held hook, a permission numeral an Approval Relay, and a reply in words to a Session parked on plain text is a peer message whose acting on is that Session's call. ADR 0014's Control Panel keeps permissions outside its question panel; this surface deliberately does not (§6). ADR 0016 is why nothing mid-turn is pushed, and its never-sliced rule is amended in exactly one place, §5's layout cut. ADR 0020 is why the table is memory only.

**What the Voice loses: nothing.** The Focus Session, the Cool-down, the Call Keeper and every voice rule are untouched; the newest-Anchor rule is this surface's own, and the two never meet.

## Legacy (ADR 0010)

`legacy@1d32845` has the Companion Channel seam and a null channel only (`bridge/channel.py`); it has **no Telegram implementation**, no reply anchoring, no buttons, no message editing, no menu and no assistant. Its one channel behaviour — mirroring every user-visible message of the Bridge's own (`bridge/channel.py:11-14`, `daemon.py:2179-2200`) — is **dropped, because** this generation's Message Switch and Cool-down exist precisely to stop that chatter (§9). The Stop Notice for every stop state, `finished` included, is **ported** (the FINISHED wording is legacy's own sentence, `bridge/host.py:226-234`, per #165 Q7). The numeral-to-label rule is **adapted** from ADR 0014's option-label rule; the assistant is **adapted** from this generation's own Delegated Turn (`adapters/call/realtime/adapter.py::delegate`). Everything else under this ADR is **new**.
